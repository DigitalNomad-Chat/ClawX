## 二、对 ClawDock 项目的兼容性分析

### 2.1 直接受影响的接口/能力

#### ✅ 低风险：RPC 方法大概率兼容

ClawDock 通过 `GatewayClient` 调用的 RPC 方法（`electron/gateway/client.ts`）：

```ts
channels.list / .get / .connect / .disconnect / .getQRCode
skills.list / .enable / .disable / .getConfig / .updateConfig / .bundles / .installBundle
chat.send / .history / .clear
cron.list / .create / .update / .delete / .run
providers.list / .set / .remove / .test
system.health / .config / .updateConfig / .version
```

这些属于 OpenClaw Gateway 的公开 RPC 面，跨版本保持兼容的概率很高。官方 Changelog 中没有提到这些方法被移除或改名。

#### ⚠️ 中风险：启动参数 / CLI 行为变化

ClawDock 启动 Gateway 时使用的参数：

```ts
['gateway', '--port', String(port), '--token', appSettings.gatewayToken, '--allow-unconfigured']
```

- `--port`、`--token` 是长期稳定的 CLI 参数，风险低。
- `--allow-unconfigured` 未见移除记录，但仍需在升级后验证。
- `2026.5.19` 将 Node.js 最低要求从 `>=22.14.0` 提高到 **>=22.19.0**。当前项目 `build/openclaw/package.json` 仍写 `>=22.14.0`；若升级到 `2026.6.6`，需要同步更新打包的 Node 运行时和 CI/发布环境。

#### ⚠️ 中风险：Plugin SDK / Extension API 路径

`electron/utils/openclaw-sdk.ts` 中为了兼容 `2026.4.5` 前后的变化，已经做了双重 fallback：

```ts
// 1. Try legacy plugin-sdk subpath (openclaw <4.5)
// 2. Try extension API file (openclaw >=4.5)
// 3. Fallback to no-op stubs
```

- 升级到 `2026.6.6` 后，需要确认 `dist/extensions/<channel>/api.js` 中的函数签名是否仍然一致。
- `2026.5.18` 引入了 `defineToolPlugin` 等 typed plugin SDK，但这主要影响新插件开发，不影响 ClawDock 当前的读取型调用。

#### ⚠️ 中风险：状态目录配置冲突

ClawDock 强制设置：

```ts
OPENCLAW_STATE_DIR: join(homedir(), '.openclaw')
```

新版本中大量状态迁移到 SQLite（auth profiles、plugin install ledger、Matrix sidecar 等）。如果 `~/.openclaw` 目录中已有旧版本生成的 state，升级后新版本的 `doctor --fix` 需要能自动迁移。ClawDock 已集成 `runOpenClawDoctorRepair`（`electron/gateway/supervisor.ts:342`），这是一个利好。

#### ⚠️ 中风险：Node 版本和 pnpm overrides

当前项目 `package.json` 中的 pnpm overrides 包含大量针对旧版本的锁定项，例如：

```json
"@anthropic-ai/sdk": "0.90.0",
"typebox": "1.1.28",
"tar": "7.5.13",
"uuid": "14.0.0"
```

OpenClaw `2026.6.6` 的依赖树可能已经更新（例如 `@anthropic-ai/sdk`、`openai`、`zod`、`typebox` 等）。如果直接升级，这些 overrides 可能需要重新校准，否则会导致运行时类型不匹配或构建失败。

#### 🔴 高风险：嵌入方式可能变化

ClawDock 的 OpenClaw 不是通过 npm registry 安装，而是通过 `build/openclaw/` 目录预打包。需要确认：

1. `2026.6.6` 的 npm tarball 结构是否仍然包含 `openclaw.mjs`、`dist/`、`skills/`、`scripts/` 等。
2. 打包脚本（electron-builder `extraResources`）是否需要调整。
3. 新的 shrinkwrap/package integrity 检查是否会影响自定义打包流程。

## 三、升级难度评估

| 维度 | 难度 | 说明 |
|---|---|---|
| **版本号/依赖声明** | ⭐ 低 | 修改 `build/openclaw/package.json` 的 `version`，更新 `node_modules/openclaw` 的 pnpm 解析。 |
| **Node.js 运行时** | ⭐⭐ 中 | 需要确保打包环境、发布产物、CI 都使用 Node >=22.19.0。 |
| **pnpm overrides 重新校准** | ⭐⭐⭐ 较高 | 大量依赖 override 需要与新版本兼容，可能需要多次迭代。 |
| **Plugin SDK/Extension API 签名验证** | ⭐⭐ 中 | 需要实际跑起来验证 `discord/telegram/slack/whatsapp` 的目标选择器是否仍然工作。 |
| **Gateway 启动和配置同步** | ⭐⭐ 中 | ClawDock 的 `config-sync.ts` 写入了 `openclaw.json` 的多个字段；新版本配置 schema 若有变化需要同步。 |
| **端到端回归测试** | ⭐⭐⭐⭐ 高 | 涉及 chat、channels、skills、cron、providers、Dreams、token usage 等多个核心流程。 |
| **Windows 打包** | ⭐⭐⭐ 较高 | `2026.6.1` 原生支持 Windows node；ClawDock 已有 Windows 相关修复，需要验证是否受益于 upstream 改进或产生新的冲突。 |

**总体评估：中等偏高难度。** 不是简单的版本号替换，但 ClawDock 已经为 OpenClaw 的演进做了不少兼容层（如 `openclaw-sdk.ts` 的 dual-path 加载），这降低了部分风险。

## 四、收益性分析

### 4.1 高价值收益

| 收益 | 影响 |
|---|---|
| **性能提升** | `2026.5.22` 的 Gateway 启动优化（/models 20s→5ms）和 `2026.6.6` 的启动延迟优化，会直接改善 ClawDock 的首次启动体验。 |
| **稳定性提升** | `2026.5.x` 和 `2026.6.5` 大量修复 agent run recovery、MCP 工具结果归一化、provider 边界、频道回复可靠性，减少运行中崩溃。 |
| **安全加固** | `2026.6.6` 的 exec approval fail-closed、MCP/sandbox/transcript 隔离，对 ClawDock 这种桌面应用尤为重要（直接访问用户文件系统）。 |
| **免费 Parallel Search** | `2026.6.5` 内置免费 web search，降低新用户配置门槛。 |
| **Windows 原生支持** | `2026.6.1` 移除 Windows node 的 Linux 依赖，可能简化 ClawDock Windows 打包和运行时。 |
| **Skill Workshop / Workboard** | 如果 ClawDock 未来要在 UI 中暴露技能治理或多 agent 编排，这些新能力是可用的基础设施。 |

### 4.2 边际收益

- **新 provider/model 支持**：NVIDIA、Cerebras、DeepInfra、MiniMax M3、Grok 4.3、DeepSeek V4、Claude Fable 5 等，扩展了可接入的模型选择。
- **TTS/语音/Matrix E2EE/Google Meet**：如果 ClawDock 未来扩展这些功能，上游已经铺好路。
- **ClawHub 安全卡/NVIDIA SkillSpector**：提升技能市场信任度。

### 4.3 收益-风险比

**结论：收益大于风险，但需要分阶段升级。**

- 当前 `2026.4.23` 已经落后约 6 周，跳过 `2026.5.x` 的稳定性修复意味着 ClawDock 用户会长期承受本可避免的问题。
- `2026.6.6` 是安全密集版本，对桌面应用至关重要。
- 主要风险集中在依赖 override、打包结构、配置 schema 和端到端回归，这些都可以通过测试覆盖。

## 五、推荐升级策略

### 方案 A：直接升级到 `2026.6.6`（推荐，但需充分测试）

**步骤：**

1. 更新 `build/openclaw/package.json` 到 `2026.6.6`。
2. 更新 `package.json` 中的 pnpm overrides，与新版本依赖对齐。
3. 确保 CI/发布环境 Node >=22.19.0。
4. 运行 `pnpm install`，检查 `node_modules/openclaw` 是否正确解析到 `2026.6.6`。
5. 验证 `electron/utils/openclaw-sdk.ts` 中的 extension API 调用是否仍返回预期函数。
6. 运行 `pnpm dev`，观察 Gateway 启动、config-sync、doctor repair 是否正常。
7. 执行端到端测试：chat.send、chat.history、channels、skills、cron、providers、Dreams。
8. 验证打包产物（mac/win）中 `resources/openclaw/` 结构完整。

### 方案 B：先升级到 `2026.5.22`（中间站）

如果担心 `2026.6.x` 的结构性变化（Skill Workshop、Workboard、Copilot 外部化）带来不稳定，可以先升级到 `2026.5.22` 这个相对成熟的中间版本，验证稳定后再上 `2026.6.6`。

### 方案 C：保持现状，仅监控

不建议。当前版本已明显落后，且 `2026.6.6` 包含重要的安全修复。

## 三、核心差距深度分析

### 差距 G1：SSE 流式传输仍是伪流式（未改善）

**当前状态**：

```
runtime-dispatch.ts:14
"This is a non-streaming implementation (streaming to be added in Phase 3)."
```

| 维度 | 原项目 | 当前项目 |
|------|--------|----------|
| **事件类型** | `draft_start` / `draft_delta` / `draft_complete` / `draft_abort` | `draft_chunk` / `draft_finalize` / `draft_abort` |
| **内容切分** | `chunkDraftContent()` 按 48 字符切分 + `setImmediate` 逐帧推送 | 无切分，轮询 `chat.history` 发现新字符后推送 delta |
| **实现方式** | ToolClient `agentRunStream` 真流式回调 | `pollHistoryForAssistantReply()` 每 3 秒轮询，最长 180 秒 |
| **前端体验** | Agent 回复逐字出现，打字机效果 | 增量追加渲染（后端仍是轮询），视觉上接近打字机但延迟更大 |

**结论**：前端通过 SSE 实现了增量追加渲染（体验改善），但后端仍然是轮询 `chat.history` 而非真流式。要彻底解决这个问题，需要将 `chat.send` 改为支持流式的 Gateway RPC，或在 Gateway 层提供流式接口。

---

### 差距 G2：任务房间（Task Room）子系统完全缺失（新增）

**原项目实现**：

原项目拥有完整的 **Hall + Room** 双系统：
- **Hall（协作大厅）**：公共群聊，围绕多个 TaskCard 进行讨论
- **Room（任务房间）**：每个 TaskCard 可绑定一个独立房间，按结构化阶段（intake → discussion → assigned → executing → review → completed）深度推进

Room 系统的核心功能：
- 房间创建/列表/详情 API
- 房间阶段流转（PATCH /stage）
- 房间消息（独立消息流）
- 房间交接/分配/审核
- 房间与 Hall 的桥接（事件互相同步）
- 房间外部桥接（Discord/Telegram）

**当前项目现状**：
- 仅有 Hall 概念，无 Room 概念
- `taskCard.roomId` 字段存在但未被使用
- 所有讨论和执行都在 Hall 的公共消息流中完成

**影响**：无法为单个复杂任务创建独立的工作空间，所有任务共享同一条消息流，信息密度高时容易混乱。

### 差距 G3：意图分类系统缺失（未改善）

**原项目实现**：

```typescript
classifyHallDiscussionFollowupIntent(userMessage)
  → "discussion_continue" → 下一位发言
  → "decision_request" → manager 收口
  → "deliverable_request" → 跳过讨论，直接执行
  → "planning_request" → planner 优先
  → "general_chat" → 不调度
```

**当前项目现状**：
- 无意图分类系统
- `operatorIntent` 始终为 `{ type: "direct_ask", text: message.content }`
- 无法根据用户消息语义自动调整调度策略

**影响**：用户说"直接出代码"时，系统仍按 discussion 模式调度；说"大家讨论一下"时，可能直接进入 execution。

### 差距 G5：看门狗/自愈/监控缺失（新增）

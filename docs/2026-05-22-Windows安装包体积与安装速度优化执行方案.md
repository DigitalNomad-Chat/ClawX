# ClawDock Windows 安装包体积与安装速度优化执行方案

> **日期**：2026-05-22  
> **状态**：计划待执行  
> **目标**：将 Windows 安装/卸载耗时从 3-5 分钟缩短至秒级  
> **风险等级**：低（第一阶段零风险，第二、三阶段可控）

## 一、现状诊断

### 1.1 核心数据

| 指标 | 当前数值 | 正常 Electron 应用参考值 |
|---|---|---|
| 安装包 `.exe` 大小 | **368 MB** | 100-300 MB |
| 解压后安装目录 | **1.9 GB** | 300-800 MB |
| 普通文件总数 | **146,102 个** | 2,000-10,000 个 |
| 安装耗时 | **3-5 分钟** | 10-30 秒 |
| 卸载耗时 | **3-5 分钟** | 5-15 秒 |

### 1.2 文件分布结构

```
win-unpacked/ (1.9 GB, 146,102 files)
├── resources/app.asar                  # 1 个文件, 154 MB   (已优化)
├── resources/app.asar.unpacked/        # 12 个文件           (原生模块)
├── resources/openclaw/                 # 1.1 GB, 140,837 files
│   ├── node_modules/                   # 281 MB, ~22,000 files
│   ├── dist/extensions/                # 936 MB, 115,963 files ← 核心问题
│   │   ├── codex/                      # 8,554 files
│   │   ├── amazon-bedrock-mantle/      # 6,910 files
│   │   ├── google/                     # 6,820 files
│   │   ├── openai/                     # 6,808 files
│   │   ├── ... (48 个扩展)
│   │   └── 每个扩展含独立 node_modules/
│   └── dist/ 其他文件                  # ~20,000 files
└── resources/openclaw-plugins/         # 4 个插件
```

### 1.3 根因定位

**根因 A：扩展 node_modules 完全冗余**
- 48 个扩展各含独立 `node_modules/`，总计 115,963 个文件、936 MB
- 验证结果：**0 个扩展拥有顶层 `openclaw/node_modules` 中不存在的包**
- Node.js 模块解析机制本身就会从扩展目录向上查找到顶层 `node_modules`（`after-pack.cjs:693` 已有注释说明）

**根因 B：开发文件混入生产包**
- 23,231 个 `.ts` 源码文件（如 `@mistralai/mistralai/src/` 被每个扩展复制一份）
- 88 个 `src/` 目录分布在 `node_modules` 中
- 这些源码在生产环境完全无用

**根因 C：NSIS 安装器的文件逐个创建模式**
- NSIS 解压 `.7z` 归档时，每创建一个文件都要触发：
  1. NTFS MFT 元数据写入
  2. Windows Defender 实时扫描
  3. 文件权限/ACL 设置
- 14.6 万次 × 上述操作 = 不可接受的 I/O 延迟

## 二、三阶段优化方案

### 阶段一：删除扩展冗余 node_modules（零风险，高收益）

**目标**：文件数减少 79%，体积减少 49%，安装/卸载速度提升 3-5 倍

#### 2.1.1 修改 `scripts/after-pack.cjs`

在 Windows 分支处理完扩展依赖合并逻辑后（第 777-808 行），增加以下操作：

1. **删除扩展本地 `node_modules/` 目录**
   - 遍历 `dist/extensions/*/node_modules/`
   - 全部 `rmSync` 删除

2. **清理扩展 `package.json` 中的依赖声明**
   - 删除 `dependencies` 和 `optionalDependencies` 字段
   - 让 Node.js `require.resolve` 自动向上查找到顶层 `openclaw/node_modules`

3. **保持 macOS 分支不变**
   - macOS 当前已有依赖去重逻辑（第 720-768 行的 `canReuseTopLevel` 路径），可以继续使用

#### 2.1.2 代码变更草案

```javascript
// after-pack.cjs —— 在扩展依赖处理完成后

// === 阶段一：删除扩展冗余 node_modules（Windows 优化）===
// 扩展的 JS 代码通过 shared chunks 加载，模块解析会向上查找到
// openclaw/node_modules/。扩展本地的 node_modules/ 与顶层完全重复，
// 可以放心删除。
if (platform === 'win32') {
  const extRoot = join(packExtDir, '..'); // dist/extensions/
  let removedExtNM = 0;
  let removedExtNMFiles = 0;

  for (const extEntry of readdirSync(extRoot, { withFileTypes: true })) {
    if (!extEntry.isDirectory()) continue;
    const extNM = join(extRoot, extEntry.name, 'node_modules');
    if (existsSync(extNM)) {
      // 统计文件数用于日志
      const count = readdirSync(extNM, { recursive: true }).length;
      rmSync(extNM, { recursive: true, force: true });
      removedExtNM++;
      removedExtNMFiles += count;
    }

    // 清理扩展 package.json 中的依赖声明
    const extPkgPath = join(extRoot, extEntry.name, 'package.json');
    if (existsSync(extPkgPath)) {
      const extPkg = readJsonSafe(extPkgPath);
      if (extPkg) {
        let modified = false;
        if (extPkg.dependencies) { delete extPkg.dependencies; modified = true; }
        if (extPkg.optionalDependencies) { delete extPkg.optionalDependencies; modified = true; }
        if (extPkg.devDependencies) { delete extPkg.devDependencies; modified = true; }
        if (modified) {
          writeFileSync(extPkgPath, JSON.stringify(extPkg, null, 2) + '\n', 'utf8');
        }
      }
    }
  }

  console.log(
    `[after-pack] ✅ Removed ${removedExtNM} extension node_modules dirs ` +
    `(${removedExtNMFiles} files), dependencies pruned from package.json.`
  );
}
```

### 阶段二：深度清理 node_modules 中的开发文件（低风险，中等收益）

**目标**：文件数再减少 10%，体积再减少 100-200 MB

#### 2.2.1 问题：清理白名单未覆盖 `src/` 目录

当前 `cleanupUnnecessaryFiles()` 的 `REMOVE_DIRS`：
```javascript
const REMOVE_DIRS = new Set([
  'test', 'tests', '__tests__', '.github', 'examples', 'example',
]);
```

**缺失**：`src/` 目录。大量 npm 包将 TypeScript 源码包含在发布的 files 中：
- `@mistralai/mistralai/src/` — 471 个 `.ts` 文件
- `@line/bot-sdk/lib/messaging-api/model` — 199 个类型文件
- `zod/src/` — 大量 locale 文件

#### 2.2.2 策略：分层的 src/ 清理规则

**安全模式**（推荐）：不删除整个 `src/` 目录，只删除其中的 `.ts` 源文件

```javascript
const REMOVE_FILE_EXTS = [
  '.d.ts', '.d.ts.map',
  '.d.mts', '.d.mts.map',
  '.d.cts', '.d.cts.map',
  '.js.map', '.mjs.map', '.cjs.map', '.ts.map',
  '.markdown',
  // === 阶段二新增 ===
  '.ts',  // TypeScript 源码
];
```

**激进模式**（可选）：直接删除 `src/` 目录，但需维护一个白名单：
```javascript
const SRC_WHITELIST = new Set([
  // 这些包的 src/ 可能在运行时被 require
  'some-package-known-to-load-from-src',
]);
```

#### 2.2.3 新增文件类型清理

| 文件类型 | 说明 | 是否可删除 |
|---|---|---|
| `.bcmap` | PDF.js 字符映射表 | ✅ 仅 PDF 预览需要，若未使用该功能可删 |
| `.proto` | Protocol Buffer 定义 | ✅ 编译后不需要 |
| `.yml` | YAML 配置文件 | ⚠️ 部分包可能运行时读取，需验证 |
| `.nycrc` | NYC 覆盖率配置 | ✅ 纯开发文件 |
| `.log` | 日志文件 | ✅ |
| `.fnt` / `.bsd` | 字体/位图数据 | ⚠️ 可能运行时用到，保守保留 |

#### 2.2.4 实施步骤

1. 增强 `cleanupUnnecessaryFiles()`：
   - 将 `.ts` 加入 `REMOVE_FILE_EXTS`
   - 将 `.proto`、`.nycrc`、`.log` 加入清理列表
2. 扩展 `cleanupUnnecessaryFiles()` 的遍历范围：
   - 当前只清理 `openclawRoot`，改为同时清理 `openclaw-plugins/*/` 和 `app.asar.unpacked/`
3. 打包验证：确认应用启动后各功能正常

### 阶段三：openclaw 归档化 + 运行时解压（中风险，高收益）

**目标**：文件数降至 ~500 个，安装/卸载达到秒级

#### 2.3.1 调研结论：传统 asar 化不可行

经深度调研，**openclaw 无法直接使用 Electron 的 asar 格式**，原因如下：

**1. 子进程启动方式决定了 asar 不兼容**
- openclaw 通过 `utilityProcess.fork()` 启动（`electron/gateway/process-launcher.ts:160`）
- `utilityProcess` 是**原生 Node.js 子进程**，不继承 Electron 主进程的 asar 透明读取能力
- Node.js 的 `fs` / `require()` 直接调用操作系统 API，无法解析 asar 归档格式
- 在 asar 内执行 `fs.readdirSync`、`fs.readFileSync`、`require('module')` 都会失败

**2. openclaw 运行时存在大量文件系统操作**
- `dist/` 内有 30+ 个文件执行 `fs.writeFile`、`fs.mkdir`、`fs.copyFile`
- 48 个扩展内部也有写操作（matrix storage、telegram bot、whatsapp creds 等）
- 启动时会扫描 `skills/`、`hooks/`、`.cursor/` 等目录
- 虽然运行时写目标主要是 `~/.openclaw/`（用户数据目录），但读操作严重依赖代码目录的树形结构

**3. 结论**
- 路径 A（子进程继承 asar 支持）：**不可行**，`ELECTRON_NO_ASAR` 对 `utilityProcess` 无效
- 路径 B（仅 asar 化 dist/）：**不可行**，子进程无法读取 asar 内的 dist 文件
- **路径 C（运行时按需解压）是唯一可行方案**

#### 2.3.2 推荐方案：安装包归档 + 首次启动解压

**核心思路**：安装包内 openclaw 以单个压缩文件存在，首次启动时由主进程解压到用户数据目录，后续直接从磁盘运行。

**架构变更**：

```
安装包内容（~500 个文件）
├── ClawDock.exe
├── resources/
│   ├── app.asar              # 主应用（1 个文件）
│   ├── openclaw.7z           # openclaw 压缩包（1 个文件, ~210MB）
│   ├── kernel/               # 独立内核（~50 个文件）
│   ├── bin/                  # 原生二进制（~20 个文件）
│   └── ...
└── ...

运行时（首次启动后）
%LOCALAPPDATA%/ClawDock/
├── openclaw/                 # 解压后的 openclaw（28,008 个文件, 934MB）
│   ├── dist/
│   ├── node_modules/
│   └── package.json
└── ...
```

**代码变更点**：

| 文件 | 改动内容 |
|---|---|
| `scripts/after-pack.cjs` | Windows 打包后将 `openclaw/` 压缩为 `openclaw.7z`，删除原目录 |
| `electron/utils/paths.ts` | `getOpenClawDir()` 在生产环境返回 `%LOCALAPPDATA%/ClawDock/openclaw` |
| `electron/main/index.ts` | 首次启动时检测 `openclaw/` 是否存在，不存在则解压 `openclaw.7z` |
| `electron-builder.yml` | `extraResources` 中的 `build/openclaw/` 改为输出 `openclaw.7z` |

#### 2.3.3 实施步骤

**步骤 1：准备 7z 压缩工具**
- Windows 使用 `7z.exe`（可从 `resources/bin/win32-x64/` 借用或内嵌）
- 或 Node.js 原生 `zlib` + `tar`（无需外部依赖，但压缩率略低）

**步骤 2：修改打包流程（after-pack.cjs）**
```javascript
// 在阶段二清理完成后，Windows 分支增加：
if (platform === 'win32') {
  const openclawSource = join(packOpenClawDir);  // resources/openclaw/
  const openclawArchive = join(packOpenClawDir, '..', 'openclaw.7z');
  
  // 使用 7z 将 openclaw/ 压缩为单个文件
  execSync(`"${sevenZipPath}" a -t7z -mx=9 "${openclawArchive}" "${openclawSource}"`);
  
  // 删除原 openclaw/ 目录，只保留 openclaw.7z
  rmSync(openclawSource, { recursive: true, force: true });
  
  console.log(`[after-pack] ✅ Compressed openclaw/ into openclaw.7z`);
}
```

**步骤 3：修改路径解析（electron/utils/paths.ts）**
```typescript
export function getOpenClawDir(): string {
  if (getElectronApp().isPackaged) {
    // 阶段三：运行时解压到用户数据目录
    if (process.platform === 'win32') {
      return join(getElectronApp().getPath('userData'), 'openclaw');
    }
    return join(process.resourcesPath, 'openclaw');
  }
  return join(__dirname, '../../node_modules/openclaw');
}
```

**步骤 4：首次启动解压逻辑（electron/main/index.ts 或 app-lifecycle.ts）**
```typescript
import { existsSync } from 'fs';
import { join } from 'path';
import { app } from 'electron';
import { execSync } from 'child_process';

function ensureOpenClawUnpacked(): void {
  if (!app.isPackaged || process.platform !== 'win32') return;
  
  const openclawDir = join(app.getPath('userData'), 'openclaw');
  if (existsSync(openclawDir)) return;  // 已解压
  
  const archivePath = join(process.resourcesPath, 'openclaw.7z');
  if (!existsSync(archivePath)) {
    console.error('[main] openclaw.7z not found');
    return;
  }
  
  // 解压到用户数据目录
  const sevenZipPath = join(process.resourcesPath, 'bin', '7z.exe');
  execSync(`"${sevenZipPath}" x "${archivePath}" -o"${openclawDir}" -y`);
  console.log('[main] ✅ Unpacked openclaw.7z to', openclawDir);
}
```

**步骤 5：卸载清理**
- NSIS 卸载程序需要额外删除 `%LOCALAPPDATA%/ClawDock/openclaw/`
- 在 `scripts/installer.nsh` 中增加卸载脚本

#### 2.3.4 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 首次启动解压耗时 10-30 秒 | 用户体验 | 添加启动屏进度条；仅首次解压 |
| 用户数据目录磁盘空间不足 | 安装失败 | 解压前检测磁盘空间；优雅降级提示 |
| 7z 工具缺失或损坏 | 无法解压 | 使用 Node.js `zlib` + `tar` 作为 fallback |
| 解压后文件损坏 | 启动失败 | 解压后校验文件哈希；损坏则重新解压 |
| 杀毒软件扫描解压文件 | 启动慢 | 签名解压后的关键可执行文件；或使用可信目录 |
| 多实例并发解压冲突 | 文件损坏 | 使用文件锁（`.unpacking.lock`）互斥 |

#### 2.3.5 回滚策略

- 改动集中在 `after-pack.cjs`、`paths.ts`、主进程启动逻辑
- 保留阶段二代码作为 fallback：若 `openclaw.7z` 不存在，则回退到 `resources/openclaw/` 原逻辑
- `getOpenClawDir()` 可设计为：先检查运行时目录，再检查 resources 目录

#### 2.3.6 与阶段二的关系

阶段三是**可选增量优化**，不依赖阶段二。即使不实施阶段三，阶段二的成果已足够显著：
- 文件数从 146,102 → 28,008（-80.8%）
- 安装包从 368MB → 210MB（-42.9%）
- 解压后体积从 1.9GB → 934MB（-50.8%）

**建议先实测阶段二的安装/卸载速度**，若已满足需求（< 60 秒），可将阶段三排期延后；若仍不达标，再投入阶段三开发。

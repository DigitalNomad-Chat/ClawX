# ClawX v0.4.8 → v0.4.10 选择性移植实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将 ClawX 上游 `v0.4.8 → v0.4.9 → v0.4.10` 的关键变更按阶段、最小文件集合、可回滚方式移植到当前 `feat/membership-system-merge-v0.4.8` 分支，保留 ClawDock 二开元数据，不一次性做完整 merge。

**Architecture:** 采用"按版本阶段分组、按子系统切分、 selective cherry-pick/patch"的策略。每个阶段产出独立可验证的 commit 链；`v0.4.9` 的 Electron IPC Runtime 重构作为独立里程碑单独处理，不混入本阶段；`v0.4.10` 的 provider 修复暂不动，直到授权。

**Tech Stack:** TypeScript / Electron / pnpm workspace / Vitest / OpenClaw bundled runtime / WebSocket gateway client

## Global Constraints

- 不得覆盖 ClawDock 二开元数据：`package.json` 中的 `name` / `version` / `upstream` / `mergeDate` / 自定义 `scripts` 必须保留。
- 不得直接 merge 整个上游 release tag；必须 cherry-pick 或 patch 方式选择性移植。
- 每个任务必须有独立的 typecheck + 相关单元测试通过才能 commit。
- `v0.4.9` IPC Runtime 重构和 `v0.4.10` provider 修复在本计划中被明确排除在当前阶段外，需单独授权。
- 所有 commit message 遵循 `<scope>: <description>` 格式，频率为"每个可验证任务一个 commit"。
- 上下文紧张时立即回传固定格式短消息：`当前步骤 / 已完成内容 / 阻塞点 / 下一步建议`，并附带分支名、最近 commit hash、最小文件集合、已跑验证命令及结果。

## 阶段切换策略

### 何时从 v0.4.8 切到 v0.4.9

### 回滚策略
- 每个 commit 保持独立；如某 cherry-pick 引入不可调和冲突，使用 `git reset --hard HEAD~1` 回退到上一个稳定 commit（注意：这会丢失未提交改动，回退前确认状态）。
- 对于大文件改动，优先使用 patch 方式而不是 checkout 覆盖，避免覆盖二开内容。

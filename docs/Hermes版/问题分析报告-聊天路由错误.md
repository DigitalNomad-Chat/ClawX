# 问题分析报告：WeChat-writer 聊天请求路由到 Default Profile

> 分析时间：2026-05-19
> 现象：前端选择 WeChat-writer 发送消息，但回复来自 Default Profile 的 Agent（"小剪"）
> 已知条件：WeChat-writer 的 Gateway 已启动，飞书对话正常

---

## 一、现象确认

### 1.1 前端行为
- 用户选择 WeChat-writer（@功能），发送消息
- `sessionKey = agent:wechat-writer:main`
- SSE 流正常返回，但内容是 Default Agent（"小剪"）的回复

### 1.2 后端行为（从日志推断）
- `[consumeChatSse] Stream started, runId=..., sessionKey=agent:wechat-writer:main`
- SSE 事件类型为 OpenAI Responses API streaming 格式
- 流正常结束，内容来自 Default Agent
- 无 `502` 或连接错误，说明请求成功到达了某个 Gateway

---

## 二、根因分析

### 2.1 信息源分裂：Config vs Runtime

后端获取 Gateway URL 涉及两个独立的信息源：

| 信息源 | 来源 | 用途 |
|--------|------|------|
| `HermesGatewayManager.gateways` Map | `startProfile()` 或 `getGatewayStatus()` | 判断 Gateway 是否运行 |
| `getGatewayPort()` | `config.yaml` → `platforms.api_server.extra.port` | 构建 API URL |

**核心问题**：这两个信息源可能不一致。

```typescript
// electron/hermes/config.ts:379
export async function getGatewayPort(profile?: string): Promise<number> {
  const config = await readConfig(profile);
  const port = config.platforms?.api_server?.extra?.port;
  if (typeof port === 'number' && port > 0) {
    return port;
  }
  return 8642;  // ← fallback 到 default 端口！
}
```

### 2.2 问题链

**Step 1**：前端发送消息
```
POST /api/chat/send
body: { sessionKey: "agent:wechat-writer:main", message: "hello" }
```

**Step 2**：后端提取 profile
```typescript
const targetProfile = extractProfileFromSessionKey("agent:wechat-writer:main");
// → "wechat-writer" ✓ 正确
```

**Step 3**：检查 Gateway 状态
```typescript
const profileStatus = hCtx.hermesGatewayManager.getProfileStatus("wechat-writer");
```

`HermesGatewayManager` 在 `main/index.ts:577` 只启动了 default profile：
```typescript
await hermesGatewayManager.startProfile('default');
```

对于 wechat-writer，`gateways` Map 中没有记录，`getProfileStatus` 返回默认值：
```typescript
{ profile: "wechat-writer", state: "stopped", port: 8642 }
```

**Step 4**：尝试自动启动
```typescript
await hCtx.hermesGatewayManager.startProfile("wechat-writer");
// → cliStartGateway("wechat-writer")
// → runHermes(['gateway', 'start'], { profile: 'wechat-writer' })
```

此时有两种可能：
- **A**：Hermes CLI 检测到 wechat-writer 的 Gateway 已在运行，返回现有状态（含正确端口）
- **B**：Hermes CLI 尝试重新启动，可能失败或返回错误状态

**Step 5**：构建 API URL
```typescript
const gatewayUrl = await hCtx.hermesGatewayManager.getGatewayApiUrl("wechat-writer");
// → getGatewayHost("wechat-writer") + getGatewayPort("wechat-writer")
```

`getGatewayPort("wechat-writer")` 从 `~/.hermes/profiles/wechat-writer/config.yaml` 读取端口。

**如果 wechat-writer 的 config.yaml 中没有配置 `platforms.api_server.extra.port`**：
```typescript
return 8642;  // fallback 到 default 端口！
```

**Step 6**：请求发到错误端口
```
POST http://127.0.0.1:8642/v1/responses
```

`8642` 是 default profile 的端口，所以请求被 default Gateway 处理，返回了"小剪"的回复。

### 2.3 为什么用户说 Gateway 已启动？

用户可能通过以下方式启动了 wechat-writer Gateway：
1. `hermes gateway start --profile wechat-writer`（Hermes CLI）
2. 或通过飞书 bot 触发启动

但无论哪种方式，如果 config.yaml 中没有配置端口，`getGatewayPort` 都会返回 `8642`。

另外，如果 wechat-writer 的 Gateway 实际运行在非 `8642` 端口（如自动分配），但 config.yaml 中没有记录，后端无法知道正确的端口。

## 四、可能的修复方案

### 方案 A：运行时状态优先（推荐）

修改 `HermesGatewayManager.getGatewayApiUrl`，优先使用运行时状态中的端口，fallback 到 config.yaml：

```typescript
async getGatewayApiUrl(profile: string): Promise<string> {
  const host = await getGatewayHost(profile);
  // 优先使用运行时状态中的端口
  const managed = this.gateways.get(profile);
  const port = managed?.status?.port || await getGatewayPort(profile);
  return `http://${host}:${port}`;
}
```

但这要求 `HermesGatewayManager` 在启动时扫描所有 profile 的状态，而不仅仅是 default。

### 方案 B：启动时扫描所有 Profile

在 `main/index.ts` 中，启动时不仅启动 default，还要检测其他 profile 是否已运行：

```typescript
const profiles = await listProfiles();
for (const p of profiles) {
  const status = await inspectGatewayStateFromFilesystem(p.name);
  if (status.state === 'running') {
    hermesGatewayManager.setProfileStatus(p.name, status); // 需要添加此方法
  }
}
```

### 方案 C：请求时动态检测

在 `gateway.ts` 中，发送请求前不仅检查 `getProfileStatus`，还要尝试从文件系统读取实际运行状态：

```typescript
const targetProfile = extractProfileFromSessionKey(body.sessionKey) || 'default';
let gatewayUrl = await hCtx.hermesGatewayManager.getGatewayApiUrl(targetProfile);

// 如果请求失败，尝试读取运行时状态
const response = await fetch(apiUrl, ...);
if (!response.ok) {
  // 尝试从文件系统读取正确的端口
  const runtimeStatus = await inspectGatewayStateFromFilesystem(targetProfile);
  if (runtimeStatus.port && runtimeStatus.port !== profileStatus.port) {
    // 使用运行时端口重试
  }
}
```

### 方案 D：使用统一的端口来源

修改 `HermesGatewayManager`，所有端口信息统一来自运行时状态（`gateway_state.json` 或 config.yaml），确保一致性：

```typescript
async getGatewayPort(profile: string): Promise<number> {
  // 1. 先检查运行时状态
  const managed = this.gateways.get(profile);
  if (managed?.status?.port && managed.status.port !== 8642) {
    return managed.status.port;
  }
  // 2. 再检查 gateway_state.json
  const state = await inspectGatewayStateFromFilesystem(profile);
  if (state.port) return state.port;
  // 3. 最后检查 config.yaml
  return getGatewayPortFromConfig(profile);
}
```

## 六、附加问题：Hermes /v1/responses 的 session 参数

即使修复了端口问题，还需要确认 Hermes Gateway 的 `/v1/responses` 是否根据 `session` 参数路由到不同的 Agent。

如果 `/v1/responses` 不根据 `session` 路由（只是会话标识），那么每个 profile 的 Gateway 本身就只处理自己的 Agent，端口的正确性就足以保证路由正确。

如果 `/v1/responses` 会根据 `session` 路由（一个 Gateway 处理多个 Agent），那还需要确保 `session` 参数的格式被 Hermes 正确识别。

建议通过 curl 直接测试 wechat-writer 的 Gateway 端口，观察回复是否来自正确的 Agent。
